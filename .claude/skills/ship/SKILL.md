# Ship skill

The last stage. `/review` reached a PASS; this turns the work into something mergeable and
leaves the merge to you. [`/continue-work`](../continue-work/SKILL.md) invokes it as its
third stage; it stays callable on its own.

Talk to the user in **unslop** prose.

## Preconditions

Refuse to start unless all three hold, and say which failed:

1. `/review` returned a **PASS** in a prior session or a prior stage. Ask if you cannot tell.
2. The branch is not `main`. Merging to `main` deploys to production.
3. The working tree's gates are green:
   ```bash
   yarn lint --write && yarn invariants && yarn typecheck && yarn test
   scripts/dev-stack.sh up && yarn e2e
   ```

## Step 1. Fold the wip spec

Only when there is one. Skip to Step 3 if the work never had a wip file.

**Choose the home.** Extend the existing area spec whenever the work changes behaviour that
spec already describes. Write a new area spec only for a genuinely new area with its own data
model and screens. Work spanning two areas updates both and cross-links; never a third file
that reads as a diff against the others. **If the work makes two specs redundant, merge them
and delete the losers** — git history keeps the originals.

**Rewrite, never append.** The area spec must read as one description of current behaviour,
not a stack of feature chapters. Delete what is no longer true. Keep everything that matters:
the *why*, the rejected alternatives, formulas, thresholds, tables. **A "superseded by #NN"
footnote is a bug in the spec, not a record** — that is the difference between an area spec
and a changelog.

Four sections are **wip-only and do not survive the fold** — `Handoff`, `Surface brief`,
`Acceptance` and `Phases`. Acceptance was scaffolding: its `[test]` claims now live in `e2e/`
as real tests named for their numbers, and the area spec states the behaviour in the present
tense instead.

Then:

```bash
rm docs/specs/wip/<nn>-<slug>.md
```

Git history keeps it. Update the row in
[`docs/specs/INDEX.md`](../../../docs/specs/INDEX.md): **one or two sentences plus tags**, in
the tone of [`section-phases.md`](../../../docs/specs/section-phases.md). A paragraph-length
row is rewritten to fit — nobody scans a paragraph.

## Step 2. Refresh the fixture, if the work earned it

Only when the work adds data every future review should see. The fixture is **generated by
the app, by script, never by hand** — hand-built fixture data drifts from the shapes the app
actually produces, and the fixture is the input to every e2e spec. The procedure and its two
traps are in [`docs/OPERATIONS.md`](../../../docs/OPERATIONS.md):

```bash
scripts/dev-stack.sh down && rm -rf .emulator-seed
scripts/dev-stack.sh up          # empty emulators
yarn fixture                     # extend e2e/fixture.build.ts first
yarn emulators:export
```

`e2e/` depends on what is in there: `SEED_USER` and the readiness markers in
`e2e/support/app.ts` wait on seeded titles. **A regenerated fixture means re-running
`yarn e2e` before you go further**, and updating those markers if the data moved.

## Step 3. Deploy rules, if they changed

```bash
GIT_VANILLA=1 git diff --name-only main...HEAD | grep -q firestore && yarn deploy:dev
```

Rules and indexes are deployed by hand to a shared dev project here, and an undeployed rule
is not a rule. Say in the PR body that this was done, so the reviewer is not left guessing
why a permission error stopped happening.

## Step 4. Commit and open the PR

```bash
GIT_VANILLA=1 git add -A
GIT_VANILLA=1 git commit -m "<type>(<scope>): <what changed>"
GIT_VANILLA=1 git push -u origin HEAD
GIT_VANILLA=1 gh pr create --draft --fill --body "Closes #<nn>"
```

**Draft, always.** Marking it ready and merging is yours — merging deploys to production.

The PR body says what changed and why, and closes the issue. If the branch carries earlier
commits that are not part of this issue, **say so in the body** — they ship with it. Never
edit the issue description; the spec link is a comment.

## Step 5. Watch CI, then stop

```bash
for _ in $(seq 30); do
  RUN=$(GIT_VANILLA=1 gh run list --branch "$(GIT_VANILLA=1 git branch --show-current)" \
          --workflow "PR" \
          --limit 1 --json databaseId --jq '.[0].databaseId')
  [ -n "$RUN" ] && break || sleep 2
done
GIT_VANILLA=1 gh run watch "$RUN" --exit-status
```

The workflow is named `PR`, in `.github/workflows/pr.yml` and here. A rename in one place and
not the other silently breaks the poll. The poll itself matters too: `gh run list` returns an
empty array for a few seconds after `gh pr create`, and an empty `$RUN` makes `gh run watch`
open an interactive picker that hangs forever in a non-interactive session.

Then **stop**. Report the PR URL, whether CI is green, what was folded and where, whether the
fixture was refreshed, and whether rules were deployed. Tell the user the PR is a draft and
the merge is theirs.

Red CI → report the failing job and stop. Do not mark a red PR ready.

## Step 6. Close out

The issue closes itself when the PR merges, via `Closes #<nn>`. Move its card to `Done` with
the sequence in [`bug`](../bug/SKILL.md) Step 2, substituting the `Done` option.

```bash
scripts/dev-stack.sh down
```

Only if you started it.
